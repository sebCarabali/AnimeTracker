- (decision) Modo fast-path elegido por el usuario; unico entregable es el spine (sin doc narrativo adicional).
- (decision) AD-1 Paradigma: Layered architecture (Controller-Service-Repository) por feature-package (auth, hoy, por-estado, tendencias, onboarding, sync), con integration.anilist como capa anti-corrupcion aislada. Prevents: logica de negocio/vistas acopladas al shape de las respuestas GraphQL de AniList; controllers llamando repositorios de otras features directamente.
- (decision) AD-2 Single-writer: solo SyncService escribe TrackingEntry y Snapshot (datos derivados de AniList). Prevents: huecos de Snapshot por escrituras paralelas no coordinadas (rompe SM-3/FR-8), dos rutas de escritura divergentes (login-sync vs job-sync).
- (decision) AD-3 AniList es fuente de verdad de estado actual; la DB propia es cache de lectura + bitacora de Snapshots, nunca autoritativa, nunca se escribe hacia AniList (ninguna mutation GraphQL en todo el codebase). Refuerza PRD §5 a nivel arquitectura.
- (decision) AD-4 Sesion/token: Spring Security + OAuth2 client contra AniList; access token guardado server-side atado a la sesion (nunca en cookie de cliente ni expuesto a Thymeleaf/JS). Token de AniList vive ~1 anio sin refresh token (verificado en docs.anilist.co) -> revocacion/expiracion se maneja como degradacion (FR-9), no como error.
- (decision) AD-5 Whitelist gate [ADOPTED de PRD OQ-1]: tabla WhitelistedUser chequeada inmediatamente post-callback OAuth, antes de crear sesion. Gestion manual (DB directa) en V1, sin UI admin.
- (decision) AD-6 Sync job: un unico @Scheduled en el mismo proceso JVM que el web app (sin worker service separado), intervalo default 45min configurable (resuelve OQ-2 dentro del rango 30-60 del PRD), concurrencia acotada (pool/semaforo de 5) para respetar el rate limit real de AniList (90 req/min, verificado en docs.anilist.co/guide/rate-limiting). Fallo de un usuario no aborta la corrida (try/catch por usuario, FR-9).
- (decision) AD-7 Login-sync reutiliza el mismo SyncService/metodo single-user que el job periodico (no un segundo codepath) para que login-sync y job-sync nunca diverjan en comportamiento (FR-7).
- (decision) AD-8 Tendencias se calculan on-read por diferencia entre Snapshots consecutivos (no se persiste un agregado semanal/mensual separado); un periodo sin Snapshot se representa como dato faltante en la query, nunca como cero (FR-5).
- (decision) AD-9 Direccion de dependencias: feature packages (hoy, por-estado, tendencias, onboarding, sync, auth) dependen de domain e integration.anilist; integration.anilist nunca depende de un feature package; ningun Controller/Thymeleaf template llama integration.anilist directo, solo via el service de su propia feature.
- (decision) AD-10 Despliegue single-instance: un contenedor Docker corriendo el monolito completo (web + scheduler in-process) + una instancia de PostgreSQL separada. Sin split worker/web a esta escala (resuelve la forma de OQ-4; el proveedor concreto queda Deferred).
- (version) Java 25 (LTS, GA sept 2025) verificado via web search como recomendacion actual para desarrollo nuevo.
- (version) Spring Boot 4.1.x (GA junio 2026, sobre Spring Framework 7, Jakarta EE 11) verificado via web; 4.0 GA fue nov 2025 asi que 4.x ya tiene ~9 meses de estabilidad. Minimo Java 17, soporte first-class Java 25.
- (version) PostgreSQL 18.x (ultima estable verificada, agosto 2026) elegido como DB propia (cache+snapshots) - boring tech, idiomatico con Spring Data JPA.
- (version) Tailwind CSS v4.3.x (ultima estable verificada julio 2026) ya fijado por el UX spine; Thymeleaf (ultima 3.x compatible con Spring Boot 4) para server-rendering.
- (version) AniList API: GraphQL endpoint publico, OAuth2 authorization-code grant, rate limit 90 req/min con burst limiter y respuesta 429 (docs.anilist.co/guide/rate-limiting), token de acceso valido 1 anio sin refresh token (docs.anilist.co/guide/auth).
- (decision) Cliente AniList via Spring RestClient (POST plano con query GraphQL + Jackson DTOs hand-mapped), sin libreria de GraphQL client/codegen (Apollo/DGS) - unico consumer de un solo endpoint, agregar una lib es sobre-ingenieria para el alcance deliberadamente chico del PRD.
- (convention) Enums de estado (TrackingStatus) mapean 1:1 a los valores de AniList MediaListStatus (CURRENT/PLANNING/COMPLETED/DROPPED/REPEATING) - nunca un enum espanol inventado en el dominio, la localizacion vive solo en las templates Thymeleaf.
- (convention) Timestamps siempre UTC Instant en DB; entidades locales mantienen su propia PK (auto-increment/UUID) mas una columna indexada separada para el id remoto de AniList (media id / anilist user id) - nunca conflar ambos ids.
- (convention) Preferencia de tema (oscuro/claro) persistida server-side como columna en el usuario (no localStorage), asi sobrevive entre dispositivos - resuelve el [ASSUMPTION] del EXPERIENCE.md.
- (convention) Config/secrets via application.yml + variables de entorno (client id/secret de AniList, credenciales DB) - nunca committeados; mutacion de datos solo a traves de SyncService (AD-2); fallas de sync se loggean y degradan (AD-4/FR-9), nunca rompen el render de pagina.
- (question) OQ-3 (retencion de Snapshots) resuelto para V1: retencion indefinida (adoptado del PRD), bajo riesgo dado el volumen (100-1000 usuarios). Revisit condition: si el conteo de filas de Snapshot se vuelve un problema de performance/costo de storage, definir agregacion/purga.
- (question) OQ-4 (hosting) resuelto en forma (single-instance Docker + Postgres separado, AD-10); proveedor concreto (VPS propio vs PaaS gestionado) queda Deferred - no bloqueante para arrancar epics/stories.
- (direction) Deferred: UI de administracion de Whitelist (OQ-1), proveedor de hosting concreto (OQ-4), escalado multi-instancia/locking distribuido del job (fuera de alcance a la escala del PRD), pre-agregacion de Tendencias para performance (prematuro), politica de purga de Snapshots (OQ-3).
- (event) Reviewer gate corrido: reconciliacion PRD/UX, rubric walker, verificacion de versiones y adversarial (4 subagentes paralelos). 0 findings criticos, varios medium/high aplicados como fixes antes de cerrar.
- (decision) Fix AD-9: contradiccion prosa/diagrama detectada (reconciliacion + rubric walker) resuelta a favor del diagrama, que es la lectura correcta para NFR §8 (dashboard nunca dispara query en vivo a AniList por carga de pagina): solo auth y sync dependen de integration.anilist; hoy/porestado/tendencias/onboarding dependen solo de domain (via read-only query service publicado por sync). Se quita el edge ambiguo domain-.->anilist del diagrama.
- (decision) Fix AD-2: sin backstop estructural (rubric walker) + sin regla de reconciliacion para bajas (reconciliacion). Los repositorios JPA de TrackingEntry/Snapshot pasan a vivir dentro del package sync (no domain), package-private; otras features solo leen via SyncedDataQueryService publicado por sync. Cada corrida de sync hace reconciliacion completa: upsert de lo presente + baja logica de TrackingEntry que ya no aparece en la respuesta de AniList (cierra FR-4).
- (decision) Fix AD-6/AD-7: gap de concurrencia (adversarial #1) - el limitador de concurrencia se mueve a integration.anilist (semaforo/pool compartido envolviendo TODA llamada a AniList), asi login-sync y job-sync comparten el mismo limite automaticamente sin importar quien los dispare. Cap default bajado a 3 (configurable) dado que AniList degrada historicamente a 30 req/min (verificado), no solo el nominal 90.
- (decision) Fix AD-7: FR-7 exige dato fresco inmediatamente post-login. Se aclara que la llamada de login-sync es sincrona/bloqueante antes del primer render post-login (unica query, no batch) - el patron de Skeleton de EXPERIENCE.md aplica a otras cargas (ej. toggle semana/mes de Tendencias), no al primer render post-login.
- (decision) Fix AD-8/ERD: granularidad de Snapshot ambigua (adversarial #2) - se fija en un row por (usuario, anime) por corrida de sync, misma cardinalidad que TrackingEntry; Tendencias suma episodios entre animes por periodo. Permite reconciliacion consistente con AD-2 y detalle por anime si se necesita a futuro.
- (decision) Fix ownership de AppUser (adversarial #3): auth es el unico owner de creacion de AppUser (findOrCreate en el login flow, despues del chequeo de whitelist, antes de crear sesion); sync nunca crea AppUser, solo lee/actualiza uno existente.
- (version) htmx 2.x (verificado via web, agosto 2026) agregado al stack para el toggle semana/mes de Tendencias sin recarga de pagina (EXPERIENCE.md) - encaja con Thymeleaf server-rendered + 'JS progresivo minimo', evita escribir fetch/DOM a mano. Thymeleaf version corregida a 3.1.x (ultima estable verificada).
- (decision) Stack: se agrega Spring Data JPA + Flyway (migraciones) - gap detectado por rubric walker (tecnologia de persistencia/migracion nunca nombrada).
- (direction) Deferred ampliado: dimension operativa (backup/restore de Postgres, logging/monitoring) nombrada explicitamente como Deferred a la decision de proveedor de hosting (AD-10) en vez de quedar silenciosa (rubric walker); AD-9 enforcement via ArchUnit test agregado como convencion, no bloqueante para V1.
- (event) spine finalized
