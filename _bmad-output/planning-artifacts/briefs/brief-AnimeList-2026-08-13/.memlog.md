- (event) Idea inicial: AnimeTracker = app web (historial/estado/calificacion/progreso de episodios) + extension de navegador (Chrome/Firefox) que detecta reproduccion en JKAnime/AnimeFLV y sincroniza progreso automaticamente en la app. Usuario pidio entrevista de 4-5 preguntas una por una cubriendo: requisitos funcionales, integraciones/limitaciones tecnicas, edge cases/no-funcionales, y out-of-scope V1.
- (event) Research digest: MAL-Sync (open-source ext) ya soporta JKAnime y AnimeFLV como sitios fuente y sincroniza con MAL/AniList/Kitsu/Simkl/Shikimori via scraping de DOM+URL por sitio. Simkl y Trakt tienen scrobblers propios (otros sitios). Deteccion tecnica = content scripts con selectores CSS/URL parsing por sitio (no generico), Manifest V3 requiere relay via background service worker para llamadas cross-origin. Modelo de datos estandar en la industria: status enum (watching/completed/on-hold/dropped/plan-to-watch), progreso episodios, rewatch count, score 1-10, fechas.
- (decision) Q1 parcial: catalogo de animes sera propio (no depende de API externa tipo Jikan/AniList para el catalogo base). Sera multi-usuario (no exclusivamente uso personal/solo-user). Pendiente: razon de diferenciacion vs MAL-Sync (por que construir en vez de usar la herramienta existente).
- (decision) PIVOT DE ARQUITECTURA (Q1 resuelta, Opcion A): AnimeTracker NO construye su propia extension de navegador. Se usa MAL-Sync (extension open-source existente) tal cual, sin modificar, para detectar reproduccion en JKAnime/AnimeFLV y escribir el progreso en una plataforma externa (AniList/MAL/Kitsu/etc via su cuenta). La app web AnimeTracker es una capa de lectura/visualizacion + valor agregado (UI propia, stats, notas) que consume el progreso via la API de esa plataforma externa (OAuth), no lo almacena como fuente de verdad. Consecuencia: el 'catalogo propio' mencionado antes queda superado -- el catalogo y el progreso viven en la plataforma externa elegida, no en base de datos propia. Pendiente de confirmar con el usuario y definir: que plataforma(s) externa(s) se integran (AniList vs MAL vs multiples).
- (decision) Plataforma externa elegida: AniList (API GraphQL, OAuth). MAL-Sync se configura para escribir progreso ahi. AnimeTracker integra via AniList API.
- (decision) AnimeTracker es de solo lectura (read-only mirror de AniList). No hay mutaciones/escritura desde la app hacia AniList. Toda edicion (estado, rating, notas) se hace en AniList o via MAL-Sync, no en AnimeTracker.
- (decision) Valor central de AnimeTracker (vs usar AniList directo): dashboard 'hoy / seguir viendo' -- que estoy mirando ahora, proximo episodio pendiente, resumen mas directo que la lista generica de AniList. Ese es el feature ancla de V1.
- (decision) Escala objetivo: ~100 usuarios en el primer anio, hasta 1000 maximo. Se hostea en un servidor/hosting que soporte Java Spring (decision de stack: backend Java Spring Boot). Tendra base de datos propia (no solo consultas en vivo a la API de AniList) -- probablemente cache/mirror de datos de AniList + posibles snapshots historicos para dashboard/stats. Pendiente confirmar: registro publico vs invitacion cerrada; que exactamente persiste en la DB propia (solo cache de sync, o tambien historial/snapshots en el tiempo).
- (decision) Registro cerrado/por invitacion (no publico), pese a la escala de 100-1000 usuarios. DB propia sirve para guardar snapshots historicos en el tiempo (tendencias tipo 'episodios vistos esta semana'), no solo cache. OUT OF SCOPE V1 (explicito del usuario): comparar listas entre usuarios, soporte para otros sitios de streaming ademas de JKAnime/AnimeFLV (delegado a MAL-Sync de todos modos), sin aplicacion movil nativa. Se suman a out-of-scope por decisiones previas: escritura/edicion desde la app (read-only), construir extension propia (se usa MAL-Sync), soporte multi-plataforma externa mas alla de AniList (MAL/Kitsu/Simkl).
